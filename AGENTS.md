## Philosophy: Multi-Model Ensemble for Higher Quality

**Core Principle**: Claude implements features faster and more accurately by consulting specialized AI models (Gemini, Codex) for validation. This ensemble approach catches edge cases, validates architectural decisions, and leverages diverse model strengths.

**Key insight**: Ensemble validation is cheap (free models) and high-yield (catches bugs, improves architecture). The cost of NOT using ensemble (debugging, rework) far exceeds the cost of using it.

**Benefits**:
- **Higher Accuracy**: Multiple perspectives catch edge cases Claude might miss
- **Faster Development**: Parallel validation vs sequential debugging
- **Better Architecture**: Cross-check with models trained differently
- **Cost Effective**: Free models reduce iteration cycles

**Usage Split**: Ensemble validation (most tasks) | Claude solo (trivial only)

## Task Implementation Methodology

The standard workflow for implementing non-trivial tasks in the codebase:

### Phase 1: Task Definition & Codebase Awareness
- Define the task: requirements, design considerations, specific steps
- Keep it concise but high-level and nuanced
- Review the codebase to find relevant existing elements
- Identify potentially redundant steps (existing functions that already solve parts of the problem)
- Prepare a codebase-aware approach before writing any code

### Phase 2: AI Consultation & Planning
Run task definition through the ensemble for analysis:
- Use CRASH for structured reasoning (2-3 steps typical, 4+ for complex)
- Select appropriate model tiers based on task complexity:
  - **Standard tasks**: `=this.gemini_daily_driver` + `codex-daily-driver-general` or `codex-daily-driver-codex`
  - **Complex tasks**: `=this.gemini_advanced` + `codex-advanced-analysis`
- Consult selected Codex + Gemini in parallel
- Gather advice on efficiency, patterns, pitfalls

> See MCP_TOOLS_REF.md for specific tool syntax and tier selection matrix

### Phase 3: Implementation (Claude Executes)
- **Screen all recommendations** for pragmaticity and relevance first
- Reject over-engineered suggestions (see Pragmatism Filter below)
- Implement the validated plan
- **Test-Driven Development is key**: Write pragmatic tests that demonstrate functionality in situ
- Tests should prove the feature works in real context, not just unit isolation

### Phase 4: Validation Pass
Run implementation through ensemble for review:
- Submit code changes for validation
- Catch errors, logic issues, edge cases
- Identify final polish opportunities

### Phase 5: Surgical Refinement
- If recommendations given, implement changes in a **minimalist, surgical manner**
- No scope creep - only address the specific issues raised
- Avoid refactoring tangential code

### Phase 6: Re-validation (Conditional)
- **If** codebase changes were made in Phase 5
- **Then** re-validate those specific changes with the AI that raised the issue
- Ensures the fix actually addresses the concern without introducing new problems

## Pragmatism Filter (Single-User Context)

**Pre-Query Context Header** (Add to AI consultant queries):
```
CONTEXT: Single-user macOS hobbyist quantitative finance tool. User is the ONLY operator.
PRIORITY: Simplicity > Complexity. Steady iteration > Endless hardening.
SKIP: Multi-tenancy, enterprise security, cross-platform, production ops.
REQUIRED: Most RELEVANT solution for personal context.
TIMEOUT: =this.default_timeout_sec seconds. Complete response within this limit or the call times out and compute is wasted.
```

**Decision Checklist** (Must pass `=this.pragmatism_pass_threshold`/`=this.pragmatism_total_checks` before implementing):

| # | Check | PASS if... | FAIL if... |
|---|-------|------------|------------|
| 1 | User-Problem Fit | Solves a problem user has NOW | Solves hypothetical future problem |
| 2 | Threat Model Reality | Defends against real threat | Defends against imaginary attacker |
| 3 | Simplest-First | 50-line script works | Suggests 500-line service |
| 4 | Current Blocker | Ignoring this blocks work | Nice-to-have, not blocking |
| 5 | Maintenance Burden | User will maintain in 6 months | One-off that will rot |
| 6 | macOS-Only | No cross-platform assumptions | Adds Linux/Windows compat |
| 7 | Defer-ability | Must do now | Can push to backlog |
| 8 | 80/20 Alternative | No simpler option exists | Simpler approach gets 80% benefit |

**Positive templates** (prefer these patterns):
- Single-binary CLI over multi-service architecture
- SQLite over networked databases
- Local scripts over containerized services
- Config files over complex permission systems
- Direct API calls over message queues

**Yellow Flags - CAUTION BEFORE IMPLEMENTING**:
- "Docker Compose"

**Red Flags - REJECT**:
- Keywords: "multi-tenant", "enterprise-ready", "microservices", "Kubernetes", "RBAC"
- If detected → Ask: "What's the single-user, single-machine alternative?"

### Disfavored → Preferred Alternatives

| Disfavored (Reject) | Preferred (Use Instead) |
|---------------------|-------------------------|
| Microservices | Single process / monolith script |
| Kubernetes / Docker Swarm | Local script or single container |
| RBAC / complex permissions | Simple config file or env vars |
| Networked database (Postgres, MySQL) | SQLite or local JSON/Parquet |
| Message queues (Kafka, RabbitMQ) | Direct function calls or simple file queue |
| API gateway | Direct HTTP or CLI invocation |
| Multi-tenant architecture | Single-user, local-first design |
| Cloud-native services | Local equivalents or single API calls |
| Enterprise auth (OAuth, SAML) | Simple API key or local config |

## When to Use Ensemble

### Claude Solo (Trivial Tasks Only)
Use solo ONLY when ALL of these apply:
- Single-line or typo-level fix
- Change is obvious and mechanical
- Zero ambiguity about correctness
- No logic changes, just formatting/naming

### Ensemble Validation (Default for Most Tasks)
**Ensemble is cheap and high-yield. Use it liberally.**

Invoke ensemble when ANY of these apply:
- [ ] Any code logic change (not just formatting)
- [ ] Multi-file changes
- [ ] New function, class, or module
- [ ] Financial calculation or money-handling logic
- [ ] Security-sensitive code (auth, crypto, permissions)
- [ ] Claude is uncertain or sees multiple valid approaches
- [ ] User explicitly requests cross-checking
- [ ] Changes > `=this.ensemble_line_threshold` lines
- [ ] Refactoring of any kind
- [ ] Bug fix where root cause wasn't immediately obvious

### When to Skip Specific Tools
**Skip deep web research for**:
- Questions answerable from codebase alone
- Standard library usage
- Patterns already demonstrated in project

**Skip CRASH structured reasoning for**:
- Simple linear tasks (read → edit → done)
- Tasks with only one viable approach

> **Note**: Ensemble (Gemini/Codex) should still be used for most code changes. The above only limits specific heavyweight tools.

### Precision-First Pivot (Hybrid Search Strategy)

Use AI-powered tools (`smart-tree`, `ai-distiller`) to establish breadth and locate target modules. Then **pivot to CLI tools** for surgical extraction and verification:

| When You Need | Pivot To | Why |
|---------------|----------|-----|
| Structural code patterns | `ast-grep -p 'pattern'` | AST-aware, no regex false positives |
| "When did this change?" | `git log -S "string"` | Commit archeology for temporal context |
| Complex config queries | `jq` / `yq` | Programmatic JSON/YAML filtering |

**Rule**: Never use regex for what an AST parser or structured query can do more accurately.

> See MCP_TOOLS_REF.md → "Precision CLI Tools" for syntax and examples.

## Best Practices

### Ensemble Validation
**DO**:
- Use ensemble liberally—it's cheap and catches bugs early
- Claude drafts first; consultants validate
- Include machine-readable output instructions
- Compare multiple model perspectives
- Use ensemble on any logic changes, not just complex ones

**DON'T**:
- Skip ensemble to "save time" (rework costs more)
- Skip Claude's analysis
- Assume consensus (models can all be wrong)
- Send API keys or secrets

### General
- Each tool definition ~100 tokens; be aware of context cost
- Use targeted queries over broad searches

### Bash Command Chaining
**Use `&&` for env vars**, not inline definitions:
```bash
# BAD: Inline var triggers per-command approval
LAKE_ROOT="/tmp/test" uv run pytest tests/

# GOOD: Chained with && uses pre-approved pattern
export LAKE_ROOT="/tmp/test" && uv run pytest tests/
```

## Codebase Understanding Strategy

> [!tip] Lead with AI tools, not grep
> The AI-powered tools (distiller, smart-tree) provide 10-100x more value than grep/glob for understanding code. Use them first; grep is for tactical lookups after you know what you're looking for.

### Phase-Based Exploration

| Phase | Goal | Primary Tool | What It Gives You |
|-------|------|--------------|-------------------|
| **1. Orientation** | Understand project layout | `smart-tree__project_overview` | Project type, tech stack, key files, structure map |
| **2. Architecture** | Map APIs and structure | `ai-distiller__distill_directory` | Class hierarchies, function signatures, exports (90-98% compression) |
| **3. Deep Dive** | Understand specific file | `ai-distiller__distill_file` | API surface without implementation noise |
| **4. Tracing** | Follow cross-cutting logic | `Task` tool (Explore agent) | Multi-file data flow, "how does X reach Y?" |
| **5. Tactical Lookup** | Find specific symbol/string | `Grep` / `Glob` (native) | Precise location of known target |
| **6. Documentation** | Domain context, requirements | `rust-local-rag__search_documents` | Indexed PDFs explaining the "why" |

### Goal-Based Tool Selection

| Your Goal | Start Here | Why |
|-----------|------------|-----|
| **Unfamiliar codebase** | `smart-tree__project_overview` → `distill_directory` on `/src` | Get the map before diving in |
| **Refactoring a module** | `distill_file` on target | See all dependencies and exports cleanly |
| **Debugging specific error** | `Grep` for error string | You have a known target—go direct |
| **Understanding business logic** | `Task` Explore agent | Cross-file tracing requires reasoning |
| **"Why was this built this way?"** | `rust-local-rag__search_documents` | Requirements/specs explain intent |
| **"When did this logic change?"** | `git log -S "string"` | Commit archeology—find exact introduction/removal |
| **Find structural code patterns** | `ast-grep -p 'pattern'` | AST-aware search respects syntax boundaries |
| **Query complex configs** | `jq` / `yq` | Programmatic JSON/YAML filtering beats regex |

### Tool Capabilities

**AI-Powered (PRIMARY)**:
- `smart-tree__project_overview`: One-call project map—type detection, key files, structure
- `ai-distiller__distill_directory`: X-ray view of directory—APIs without implementation
- `ai-distiller__distill_file`: Single-file API extraction (90-98% token reduction)

### Precision CLI Tools

> [!tip] Surgical tools for when AI output is too broad
> These CLI utilities bridge AI-driven discovery and manual inspection. Use them for strict structural/temporal accuracy where regex fails.

**Structural Search (AST-aware)**:
- `ast-grep` (alias: `sg`): Pattern matching on syntax trees, not text
  ```bash
  # Find all fetch() calls with two arguments
  sg -l ts -p 'fetch($URL, $OPTS)' src/

  # Find class definitions extending a base
  sg -l ts -p 'class $NAME extends $BASE { $$$ }' src/
  ```
  - **Use when**: Structural matches needed (avoid false positives in comments/strings)
  - **Avoid when**: Simple literal search suffices (use `git grep` for speed)
  - **Note**: Has MCP server (`ast-grep-mcp`) — future toolgroup candidate

**Temporal Search (Git History)**:
- `git log -S "string"`: Pickaxe search — find when exact string was added/removed
  ```bash
  # When was DEFAULT_TIMEOUT_MS introduced?
  git log -S 'DEFAULT_TIMEOUT_MS' -p --oneline -- src/
  ```
- `git log -G "regex"`: Regex search in diffs — find commits touching pattern
  ```bash
  # Find all commits that modified setTimeout calls
  git log -G 'setTimeout\(' -p --oneline -- src/
  ```
- `git grep "pattern"`: Search current HEAD (faster than grep, respects .gitignore)
  ```bash
  # Find current usages of a feature flag
  git grep -n -F 'isFeatureEnabled(' HEAD -- src/
  ```
  - **Use when**: "When did this change?" or "Who added this?" questions
  - **Avoid when**: Only need current state (use native `Grep`)

**Structured Data Querying**:
- `jq`: JSON querying with filters and selectors
  ```bash
  # Find all failed tests and extract error messages
  jq -r '.tests[] | select(.status=="failed") | .error.message' results.json

  # Get nested config with fallback
  jq -r '.config.database.host // "localhost"' config.json
  ```
- `yq`: YAML querying (jq-like syntax)
  ```bash
  # Extract the "Run tests" step from GitHub Actions
  yq e -r '.jobs.build.steps[] | select(.name == "Run tests") | .run' .github/workflows/ci.yml

  # Get container image from K8s deployment
  yq e -r '.spec.template.spec.containers[] | select(.name == "api") | .image' deployment.yaml
  ```
  - **Use when**: Config-heavy projects (K8s, CI/CD, complex package.json)
  - **Avoid when**: Simple key lookup (just `Read` the file)
  - **Caveat**: `yq` syntax varies by version — check `yq --version`

### Anti-Patterns

| Don't Do This | Do This Instead |
|---------------|-----------------|
| Grep for common terms (`user`, `config`) in large repos | Distill first to narrow scope |
| Read raw implementation to understand API design | Use `distill_file` for clean API view |
| Manually recurse through directories | `smart-tree__project_overview` in one call |
| Ignore indexed docs when code logic seems arbitrary | Query RAG for requirements/specs |
| Start with grep on unfamiliar codebase | Start with `smart-tree` → `distill_directory` |
| Use regex for nested code structures (callbacks, class shapes) | Use `ast-grep` for syntax-aware structural matching |
| Debug regressions without checking history | Use `git log -S` to find when failing logic was introduced |
| Scroll through massive JSON/YAML to find keys | Pipe to `jq` or `yq` for filtered, targeted output |

## Failure Modes & Fallbacks

**Principle**: Never block on a broken tool. Follow retry protocol, then degrade gracefully.

### Gemini Timeout/Error Protocol
1. **Retry 1**: Rerun with same prompt
2. **Retry 2**: Narrow prompt dramatically (focus on core question)
3. **Skip**: If still fails, skip Gemini FOR THIS CALL ONLY. Use Qwen (`=this.qwen_model`) as replacement.
4. **Resume**: Continue trying Gemini for future calls (not permanently disabled)

### Codex Timeout/Error Protocol
1. **Retry 1**: If daily-driver, try same query. If advanced, ensure timeout=`=this.codex_advanced_timeout`
2. **Retry 2**: Narrow prompt dramatically + max timeout
3. **Skip**: If still fails, skip Codex FOR THIS CALL ONLY. Use Qwen as replacement.
4. **Resume**: Continue trying Codex for future calls

> [!tip] **Non-timeout failures** (schema errors, malformed output, safety refusals): Skip immediately—go straight to Qwen backup. No retries needed.

### Fallback Hierarchy

| Failure | Fallback Action |
|---------|-----------------|
| Gemini fails (after retries) | Use Qwen (`=this.qwen_model`) for that validation round |
| Codex fails (after retries) | Use Qwen for that validation round |
| Both Tier 1 fail | Use Qwen as sole validator for that round |
| Qwen also fails | Claude proceeds solo with explicit uncertainty note |
| Web search unavailable | Use local RAG if docs indexed, else proceed with knowledge |
| Local RAG empty/error | Use native Grep/Glob on codebase instead |
| CRASH MCP error | Use inline reasoning in response |

**When to abort vs continue**:
- **Abort**: User explicitly requested ensemble and ALL models (including Qwen) failed
- **Continue**: Tool failure is incidental; Qwen backup or solo reasoning sufficient

## Multi-Model Consensus Strategy

### Why Ensemble Matters

Gemini + Codex consensus is **cheap and high-yield**:
- **Zero API cost** (both use free CLI bridges)
- **Catches blind spots** (models trained differently find different issues)
- **Validates assumptions** (consensus = confidence, disagreement = investigate)
- **Primary pair**: Gemini and Codex are the core validators; Qwen is backup only

### Consensus Interpretation

| Pattern | Meaning | Action |
|---------|---------|--------|
| Gemini + Codex agree | High confidence | Proceed with implementation |
| Gemini + Codex disagree | Investigate | Dig into the disagreement, use CRASH if needed |
| One fails, other passes | Moderate confidence | Proceed but note the gap |
| Both fail | Degraded validation | Use Qwen backup, note uncertainty |

### Strategic Model Selection

**Speed vs Depth tradeoff**:
- Daily-driver/Flash: 10-30s response, sufficient for 80% of tasks
- Advanced/Pro: 30-120s response, necessary for complex/risky tasks

**Cost-benefit analysis**: Time spent on advanced validation should correlate with:
- Risk of the change (financial, security, breaking)
- Complexity of the decision (multi-file, architecture)
- Reversibility (hard to undo = more validation)

## Local Additions
## Project Summary

`rust-local-rag` is a Rust MCP server that provides **local RAG** (Retrieval-Augmented Generation) over a directory of PDFs:

- Extracts PDF text locally (primary: `lopdf`; fallback: `pdftotext` when available)
- Chunks text (sentence-aware), embeds chunks via **local Ollama**, persists embeddings locally (per-model indexes)
- Serves MCP tools + job orchestration for background indexing to avoid timeouts
- Also exposes HTTP endpoints used by the TUI and the evaluation harness

## Engineering Guardrails (important invariants)

**Warnings are errors**:
- `.cargo/config.toml` sets `-D warnings`. Keep builds/clippy warning-free.

**Async + blocking work**:
- Do not block Tokio runtime. Use `tokio::task::spawn_blocking` for CPU-bound / blocking work (PDF extraction, embedding calls, heavy parsing).

**Locks**:
- The shared engine is `Arc<RwLock<RagEngine>>`. Keep write locks short.
- Indexing uses per-document locking; don't reintroduce "hold write lock for entire reindex" behavior.

**Jobs**:
- Reindexing runs as background jobs (SQLite persistence + supervisor).
- Preserve "single active reindex job" semantics (atomic check-and-create).
- Poison-pill behavior: a single document failure should not abort the whole job.

**Persistence**:
- Indexes are model-partitioned (`chunks_{sanitized_model}.json`), plus SHA-256 document hashes.
- If you change persistence format/semantics, add a migration path and update docs.
