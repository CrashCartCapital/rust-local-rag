## Timeout Hierarchy (CRITICAL)

**Outer workflow timeout MUST exceed inner tool timeouts.**

Rule of thumb:
- Parallel: `outer >= max(inner) + 60`
- Serial: `outer >= sum(inner) + 60`

Execution types (naming may vary by repo integration):
- Ephemeral script workflows: prefer for heavy/one-off flows (set outer timeout up to `=this.ephemeral_timeout_with_codex`s when Codex is involved).
- Saved/library workflows: prefer for reusable, smaller flows (keep outer timeout ≤`=this.library_timeout_max`s).

## Core Primitives

- `pipe()` for sequential steps (fetch → process → store).
- `parallel()` for independent steps (gather multiple sources).
- `chain()` for mixed execution (parallel gather → serial merge).

1. Search existing workflows first.

## Test-Driven Development (TDD)
TDD is required for:
- New functions/classes/modules
- Any logic/behavior change
- Bug fixes (regression test required)

If behavior is unchanged: run existing tests; add missing coverage only if gaps block confidence.

**Trivial Skip Criteria** (ALL must be true):
- Change is ≤5 lines of code
- No new functions, classes, or methods
- Change is docs/config/typo only

### Stateful TDD Workflow

TDD is a **gated state machine**. Do not proceed without completing each state.
States:
- RED: write the failing test (prove the spec exists).
- GREEN: implement minimally until the test passes.
- REFACTOR: clean up while keeping the suite green.

### Evidence Requirements

Evidence is required for RED and GREEN (and ideally for full-suite after refactor):
- RED: pasted output showing the test fails.
- GREEN: pasted output showing the test passes.
- REFACTOR: pasted output showing the relevant suite still passes.

### Anti-Cheat Rules

These patterns indicate TDD evasion:
- `skip` / `xfail` to avoid enforcement
- Trivial assertions (`assert True`, `is not None`) instead of behavioral checks
- Weakening assertions to “make it green”
- Over-mocking so the behavior isn’t exercised

**Rule**: If you use skip/xfail, document explicit user approval in the commit message.

### Traceability

For medium/large changes, include a short mapping of:
- PRD task → test id(s) → test file → what the assertions prove

**Naming convention**: `test_prd_{task_id}_{description}`

---

## Pre-Commit Checklist

Before committing:
- TDD followed when required (RED → GREEN → REFACTOR)
- Evidence captured for RED + GREEN
- Relevant tests pass
- Lint/typecheck pass (if configured)
- No `skip`/`xfail` without explicit approval
- Commit message format is correct

**Commit format**: `<type>(<scope>): <description> [PRD:<task-id>]`

---

## Environment Edge Cases

### Tests Cannot Run

If test harness is broken/missing:
1. **STOP** and inform user
2. If user approves continuing:
   - Still **write** the test code
   - Document expected failure reason
   - Write implementation
   - Mark with: `[Tests written, not executed - env issue]`
3. Run tests when environment is fixed

### Test Command Unknown

Check in order:
1. `pytest` / `python -m pytest`
2. `cargo test`
3. `npm test` / `deno test`
4. `make test`
5. Check `pyproject.toml`, `package.json`, `Makefile`

If still unknown: **STOP** and ask user.

## Quick Reference

### TDD States
```

```

### Evidence Template

**Role**: Distributed compute - offload heavy work from laptop

**Role**: Personal knowledge ETL - aggregate and search saved content

**Role**: RAG engine - semantic search as a service or library

- **Server**: Rust MCP server (Streamable HTTP) on port 8140

- **Use**: PCA can embed ragcore directly; other tools call MCP

# Remote AI Agent Deployment Guide

Purpose: guidance for autonomous agents running in cloud VMs (Jules, Copilot Workspace, Codex API).

> For local Claude Code methodology, see `@GENERAL_GUIDANCE.md`
> For MCP tools, see `@MCP_TOOLS_REF.md`

---

## Reality (Non-Negotiable)

Assume the agent has:
- Public internet + the target git repo + package registries
- CI runner access (if configured)

Assume the agent does *not* have:
- Home LAN/NAS, local daemons, local MCP servers (1MCP/mcpjungle), or local secrets unless explicitly configured

## Standing Orders

- Be specific and scoped (no “make it better”).
- Keep diffs small (one theme per PR).
- Definition of done must be verifiable (lint/typecheck/test output in PR).
- If blocked, document blocker and stop (don’t guess).

Strict preamble (paste at top of remote-agent prompts):
```text
ENV: cloud VM. No LAN/NAS. No local MCP/1MCP/mcpjungle. No secrets unless configured.
RULES: small diffs, no unrelated refactors, run verification and paste output.
BLOCKED: document and stop.
```

## What To Send Remote Agents

Good:
- Lint/format fixes, test fixes, dependency bumps, small refactors, documentation updates

Avoid:
- Anything requiring NAS/data lake access
- Multi-repo integration work
- “Research semantics” changes in `CCC_lab` without tests/validation

## One Prompt Template (Covers Most Use Cases)

```markdown
## Task: <concise title>

ENV: cloud VM. No LAN/NAS. No local MCP tools. No secrets unless configured.

### Objective
<what to accomplish>

### Scope
- ONLY touch: <paths>
- DO NOT touch: <paths>
- NO refactors unless required for the objective

### Verification (must run + paste output)
1. <lint command>
2. <typecheck command>
3. <test command>

### Definition of Done
- Verification passes
- Diff is within scope
- New/updated tests cover behavior change (if any)

### If Blocked
- Write a short blocker note and stop
```

## Human Review Checklist

- Scope stayed bounded; no opportunistic refactors.
- Verification output is present and matches the diff.
- No secrets/credentials added.

- Copilot Workspace: specify paths explicitly; keep tasks small.

# Preferred Documentation & Git Rules

Purpose: standards for documentation + git workflows across projects.

## Documentation Hierarchy

### What Goes Where

- `README.md`: humans; minimal quickstart.
- `CLAUDE.md`: AI context for the repo (architecture, commands, patterns, imports).
- `AGENTS.md`: multi-agent coordination rules (handoffs, boundaries).
- `GEMINI.md`: only if Gemini needs different instructions.
- Code comments: “why”, not “what”.
- Docstrings/JSDoc: public API contracts.

### README.md Guidelines

**Keep it minimal**. Humans skim; AI needs detail elsewhere.

**Avoid in README**:
- Architecture diagrams (put in CLAUDE.md)
- Detailed API docs (use docstrings)
- Configuration reference (use .env.example + code)
- Troubleshooting guides (use GitHub Issues/Discussions)

## Git Workflow

### Branch Naming

- Pattern: `type/short-description` (e.g. `feat/add-rsi-indicator`, `fix/duckdb-lock-timeout`).

### Commit Messages

- Pattern: `type(scope): short description` (e.g. `fix(storage): handle concurrent DuckDB writes`).

**Types**: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`

**Scope**: Optional, indicates affected module

### Commit Atomicity

- Avoid mixing concerns in one commit; prefer one change theme per commit.

## Version Control Rules

### What to Commit

- Commit: source code, lockfiles, docs, test fixtures (small), `.env.example`.
- Don’t commit: secrets (`.env`, keys), `node_modules/`, `.venv/`, IDE settings.

### Lockfile Policy

**Always commit lockfiles**:
- `uv.lock` (Python)
- `deno.lock` (Deno)
- `Cargo.lock` (Rust binaries)
- `package-lock.json` (Node)

**Why**: Reproducible builds, consistent CI, dependency security.

### Secret Management

- Never commit: `.env`, credentials, `*.pem`, `*.key`.
- Do commit: `.env.example` (with `${ENV_VAR}` placeholders).

**Pattern**: Use `${ENV_VAR}` placeholders in committed configs.

## Project Summary

`rust-local-rag` is a Rust MCP server that provides **local RAG** (Retrieval-Augmented Generation) over a directory of PDFs:

- Extracts PDF text locally (primary: `lopdf`; fallback: `pdftotext` when available)
- Chunks text (sentence-aware), embeds chunks via **local Ollama**, persists embeddings locally (per-model indexes)
- Serves MCP tools + job orchestration for background indexing to avoid timeouts
- Also exposes HTTP endpoints used by the TUI and the evaluation harness

## Engineering Guardrails (important invariants)

**Warnings are errors**:
- `.cargo/config.toml` sets `-D warnings`. Keep builds/clippy warning-free.

**Async + blocking work**:
- Do not block Tokio runtime. Use `tokio::task::spawn_blocking` for CPU-bound / blocking work (PDF extraction, embedding calls, heavy parsing).

**Locks**:
- The shared engine is `Arc<RwLock<RagEngine>>`. Keep write locks short.
- Indexing uses per-document locking; don't reintroduce "hold write lock for entire reindex" behavior.

**Jobs**:
- Reindexing runs as background jobs (SQLite persistence + supervisor).
- Preserve "single active reindex job" semantics (atomic check-and-create).
- Poison-pill behavior: a single document failure should not abort the whole job.

**Persistence**:
- Indexes are model-partitioned (`chunks_{sanitized_model}.json`), plus SHA-256 document hashes.
- If you change persistence format/semantics, add a migration path and update docs.
